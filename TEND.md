- **Real, pre-existing dead code found during survey**: the old "Reply thread panel" JS listened for a click on `#open-replies` — an id that was deleted from the markup back in LIME-06, when the hardcoded thread messages it lived on were removed. Its early-return guard (`if (!openReplies) return`) has silently fired on every page load since, meaning the back-to-profile button never worked either, despite still existing in the markup. Any avatar added afterward — every message sent via the main composer since LIME-07, and now every reply — rendered as a blank circle with no initials or color, since nothing re-ran that logic. Promoted it to a reusable top-level function; `handleSend` (LIME-07) and the new reply-rendering code both now call it explicitly on their own newly-inserted avatars.
- Seed data reality check before building anything: only one real reply existed in the entire dataset (`msg-004` → `msg-003`), despite `msg-003` itself claiming `reply_count: 4`. Added 2 more sample replies (`msg-1004`, `msg-1005`) to `seed-data/messages.json`, keeping them from the only two people who could realistically be in that thread — `conv-001` is a 1:1 DM between just Jean Chung and Shem Robinson, so a reply from anyone else (the old hardcoded panel's "Mary Lee"/"Valene Rajoon" weren't even participants in that conversation) would have been the exact same coherence bug flagged back in LIME-04a. Regenerated the embedded `public/js/seed-data.js` mirror from the updated source, per the process established in LIME-06. `reply_count`/`last_reply_at` are treated as decorative/stale metadata, never trusted for a displayed count — `getRepliesForMessage()` always computes the real list from actual `reply_to` relationships, the same principle already applied to reactions in LIME-08.

The expand/collapse/auto-grow/is-active JS logic itself is a second, separate block, not a shared function — this brief's scope explicitly excludes touching the main composer, and merging the two would mean editing that already-working code.
- Promoted `presenceFor`/`shortName`/`escapeHtml`/`formatTime`/`formatDay`/`formatDuration`/`previewFor` out of the LIME-06 closure to top-level scope so the new reply code could reuse them — all were already pure, parameter-only functions with no dependency on that closure's own state, so this changes nothing about how the existing contacts/thread code uses them. Added a new `plainPreviewFor()` (text-only, no icon markup) for the reply quote, rather than stripping HTML out of `previewFor`'s output.
- **Known characteristic, not a new bug**: replies (both the existing `msg-004` and the 2 new sample ones) also appear in the main thread's own flat scroll, since `getMessagesByConversation` was already returning every message in a conversation regardless of `reply_to` — this predates this brief. - **Not fixed, flagged only**: the profile-opening click handler (`.lime-message__sender, .lime-message .lime-avatar` → open profile panel) has the exact same one-time-`forEach` staleness bug `paintAvatar` had — it only wires up whichever messages existed at page-load time, so clicking a name/avatar in a conversation switched to *after* load, or on a freshly-sent message, does nothing. Real, but unrelated to this brief's goal and not required for it — named here rather than silently fixed, since fixing it wasn't asked for.
- Verified via source inspection only — brace/tag balance across all three touched files, `app.js`/`data.js` syntax checks, confirmed the `getComputedStyle`-style introspection isn't available in this sandbox (Firefox preview only, no scripting access). ## LIME-12 — Fix Mobile Nav

- **Surveyed before touching anything, since this area predates this session's own work**: the mobile drawer's actual implementation lives mostly in `vendor/seed/components/layout/layout.css`, not `lime.css` — Lime only adds the trigger button + its own backdrop (`.lime-mobile-nav-backdrop`), reusing Seed's `.seed-layout--mobile-open` mechanism for the panel itself (real class name; the brief's guessed `.seed-layout--mobile-nav-open` doesn't exist).
- **Root cause identified, not guessed**: Seed's own mobile treatment for this panel is a floating, *inset* card (`top/left/bottom: 16px`, not flush against any edge) toggled via `display: none` ↔ `flex` — and `display` changes can never be animated by a CSS transition, full stop. That combination (inset on every side, zero slide animation) is very plausibly what read as "floating icons over content, not a proper drawer" — not a separate bug causing individual icons to render disconnected. Checked for one anyway: nothing in this app's own sidebar/nav CSS sets `position: fixed` or `absolute`, and Seed's own unused `.seed-layout__reveal-*`/`.seed-layout__backdrop` rules are inert since Lime's markup never includes those elements. No stray-positioned elements exist to hide (item 5's ask), and the JS toggle (item 4) already correctly adds/removes the right classes on hamburger/backdrop/Escape — verified against the actual code, not assumed, before deciding no JS change was needed.
- Implemented items 1/2/4 as: keep the panel always "displayed" (`display: flex`, not Seed's `display: none` at rest) but parked off-screen at `left: -100%`, sliding to `left: 0` on `.seed-layout--mobile-open` — `left` *can* animate, unlike `display`, so `transition: left 0.2s ease` (item 1's own ask) actually does something now.
- **Real specificity bug caught and fixed before it shipped as a half-working hybrid**: Seed's own `.seed-layout--mobile-open .seed-layout__left` rule is 2-class specificity — higher than a single-class override rule, so it would have kept winning for every property except the one I explicitly restated (`left`), regardless of source order. A first draft that only overrode `left` would have produced a genuine hybrid: edge-to-edge horizontally (from the new rule) but still inset top/bottom at Seed's old 16px values and the old, narrower `min(260px, 75vw)` width (from Seed's rule, since specificity beats source order). Fixed by restating every property (`display`/`position`/`top`/`bottom`/`width`/`z-index`) in the override, not just the one this brief happened to mention.
- Left `.lime-mobile-nav-backdrop`'s existing overlay color (`rgba(19, 27, 23, 0.3)`, Seed's own "soil" dark tone) unchanged rather than replacing it with the brief's literal `rgba(0,0,0,0.3)` — the current value already matches Seed's own backdrop treatment used consistently elsewhere in this app (the search modal's backdrop, and Seed's own inert `.seed-layout__backdrop` rule), and swapping to a generic black would have been the one inconsistent backdrop color in the app.
- Attempted to verify by resizing the Firefox window to a mobile-narrow width via AppleScript before opening the page — the command ran without error, but with no way to read back window state or take a screenshot in this sandbox, I have no way to confirm whether it actually took effect. This brief's own gate ("test on mobile viewport") genuinely needs the user's own device/browser check; nothing here was verified visually.

- **Full model change, not a bug fix**: reverted LIME-12's `position: fixed` overlay entirely. `.seed-layout__left` goes back to being a normal grid item; the grid's own `grid-template-columns` now animates `0px 1fr` → `280px 1fr` on `.seed-layout--mobile-open`, so opening the nav actually resizes the layout (pushing `.seed-layout__center` into the second column) rather than floating on top of it. Added a matching-specificity override so the collapsed-left leftover can never interfere at this breakpoint (a mobile user should never see that state at all — its own toggle is already hidden here).
- **Second real bug caught via live introspection**: even after that fix, `.seed-layout__center` was measured landing in grid column 1 — the same horizontal position as `.seed-layout__left`, visibly overlapping it — despite neither element having any `grid-column`, `order`, or `display` override that should cause that (checked all three directly against the live DOM, not assumed). Reverified after: center panel's left edge moved from 0 to 296 (280px column + 16px gap) — confirmed via the same live-introspection technique, not assumed fixed.
- **Known minor cosmetic gap, not chased further**: the open sidebar measures 260px wide, not the intended 280px (its grid column is correctly 280px; something knocks 20px off the element's own rendered width). `box-sizing: border-box` is already correctly set, ruling that out as the cause.
