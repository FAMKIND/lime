# Calls on Android: the survey and the plan (LIME-402)

Read-only survey for plot (written on the `android` branch, night 3). No code was changed and no dependency was added. **Nothing below was tried on a device or emulator**: it is from reading the iOS files, LimeCore and the two server functions, plus one fetch of LiveKit's Android README. Anything not confirmed from those is marked **unverified** (it comes from memory of Android's documentation and must be checked against developer.android.com and Google Play Console help before it becomes a brief).

What iOS has today, by size (lines): `ios/Lime/Core/Calls/CallManager.swift` 901 (1:1 signalling machine), `CallMedia.swift` 645 (1:1 media over stasel/WebRTC 152.0.0), `GroupCallManager.swift` 1,024, `GroupCallMedia.swift`/`GroupCallNetwork.swift` (LiveKit Swift SDK 2.17.0, `ios/project.yml`), `CallKitSystem.swift` 173, `CallPiP.swift` 333, `PiPGridPlan.swift` 117, `CallRoute.swift` 87, `StoreSignalling.swift` 60; the screens are `ios/Lime/Features/Calls/*` (CallView, GroupCallView, CallsTab, CallMiniPlayer, CallAccessibility). Core already holds: `client/calls.rs` (67 lines: `send_call_signal`, `fetch_turn_servers`), `client/group_calls.rs` (310 lines: `start_group_call`, `join_group_call`, `leave_group_call`, `recover_group_calls`, `take_group_call_events`, `deliver_group_call_ops`, `fetch_livekit_token`, the sender-key calls), and `store/calls.rs` / `store/group_calls.rs` (history and events).

## 1. The call phases, who decides what, and what can go into core

`CallPhase` is `idle`, `outgoing` (I called), `incoming`, `connecting` (answered; media coming up), `active` (`CallManager.swift:6`). Today **Swift decides everything between the signals**: the phases and their timeouts (ten seconds of "Calling…" with no `call.ringing`, then a hint), busy and unavailable answers, glare (both call at once), the breakthrough rule, renegotiation, the `call.offer` / `call.answer` / `call.ice` / `call.ringing` / `lime-ctl` ops and the DTLS fingerprint check (`docs/android.md` row 23, about 560 lines), the group call decisions (row 24, about 400 lines: ring or invite, stuck tiles, which subject to show, the poll interval), the call history rules (row 22: grouping, outcome words, missed counting, call back or join, the call bubble parse) and the PiP grid plan (row 25). The core only stores events and history and sends the ops.

**Proposal: `core/src/client/call_rules.rs` first, before any Android call UI** (the core-first rule, `lime-core-first-android`): `call_machine_step(state, event) -> (state, actions)` for 1:1 (events: user taps, signals received, timers fired, media connected/failed; actions: send op, start/stop ringing, start media, show a hint, end with a reason), the same shape for group calls, `group_calls(records)` and `call_outcome_words` for the Calls tab, `pip_grid_plan(...)`. Media, the system call UI and PiP stay platform code. This is a big move (about 1,100 lines of Swift plus tests), so it is its own brief and iOS adopts it later (LIME-133b), exactly as with the night-3 rules.

## 2. The media layer

- **1:1 media.** iOS uses a plain Google WebRTC build (stasel/WebRTC 152.0.0) with the app's own offer/answer and the TURN servers from `turn-credentials`. Android needs a WebRTC library for it. **Decision for the user** (not mine): (a) LiveKit's Android SDK brings its own native WebRTC (its README says it "includes native WebRTC libraries" for arm64-v8a, armeabi-v7a, x86, x86_64; the Maven artifact of that WebRTC build is not stated on the page: **unverified**), so one dependency could serve both 1:1 and group calls; but its API is room-based, so a 1:1 call would join a room instead of exchanging SDP (a different design from iOS and from `call.offer`), or (b) a separate WebRTC artifact for 1:1 (which one is a research item: **unverified**; Google no longer publishes `org.webrtc` on Maven Central as far as I remember, **unverified**) and LiveKit only for groups, which mirrors iOS exactly (two libraries). I recommend (b) for parity and so the `call.*` signalling and its tests carry over; the cost is two WebRTC copies in the APK (size: **unverified**, likely tens of MB).
- **Group media.** LiveKit **Android SDK 2.30.0** (the README's install line; its Swift counterpart on iOS is 2.17.0, they are versioned separately), **Apache-2.0**, needs JitPack as an extra Maven repository as well as Google and Maven Central (README), optional `livekit-android-camerax` and `livekit-android-track-processors` add-ons, Compose components in a separate repository (`livekit/components-android`). **minSdk: not stated** on the README or quickstart (**unverified**; lime's minSdk is 26). Group calls use the sender-key end-to-end frame encryption (`GroupCallMedia.swift:69-135`, GCM, every key in slot 0 because the Swift SDK cannot pick a slot, LIME-163): the Android SDK's key-provider API must be checked for the same (**unverified**); this is the biggest technical risk of the group brief.
- **Permissions.** `RECORD_AUDIO` and `CAMERA` (runtime; LiveKit's pages say it relies on both), `BLUETOOTH_CONNECT` (runtime on API 31+, for headset routing: **unverified** in detail), `MODIFY_AUDIO_SETTINGS`, `INTERNET` (have). No screen share in lime, so no `MediaProjection`.
- **Foreground service for an active call.** An ongoing call must survive the screen turning off and the app leaving the front: a foreground service with a type; the candidates are `phoneCall` (API 34+, needs `FOREGROUND_SERVICE_PHONE_CALL`, and the app must hold a Telecom registration or `MANAGE_OWN_CALLS`), or `microphone` and `camera` types while they are in use (**unverified**; the LiveKit pages do not mention a service type). **Google Play needs a declaration for the type** (roadmap item a4 in `PLOT-ANDROID.md`).
- **minSdk 26 consequences:** self-managed Telecom is available from API 26 (**unverified**), PiP from API 26 (**unverified**), Bluetooth routing differs below API 31 (`startBluetoothSco` before, `setCommunicationDevice` from API 31: **unverified**), the notification-permission prompt only from API 33 (lime already handles it for messages).

## 3. The Android calling surface

| Need | Option A | Option B | Notes |
|---|---|---|---|
| Incoming and ongoing call, system-level | Telecom `ConnectionService`, **self-managed** (the Android twin of CallKit: audio focus, a call shown to Bluetooth/car/watch, other calls put on hold) | A high-priority notification with Answer and Decline plus the app's own screen | A is closer to iOS (`CallKitSystem.swift`); B is far less code and works without Telecom quirks. **Decision for the user.** |
| Ring when the phone is locked | Full-screen intent notification | Heads-up notification only | Since API 34 full-screen intents are restricted to calling and alarm apps and the user can revoke the permission (`USE_FULL_SCREEN_INTENT`; Play asks for a declaration): **unverified**. Without it the lock-screen ring is a plain heads-up. |
| Ring when the app is closed | Needs a push | Not possible | **There is no push on either platform until DESIGN-37** (decided 2026-11-10: FCM, wake-up only). Until then an incoming call can only ring while lime is open or in the foreground service; this is the single largest limit on calls and should be said to the user plainly. |
| Speaker, earpiece, Bluetooth | `AudioManager` routing (communication device on API 31+) | Telecom's audio route API (if A above) | See minSdk notes. |
| Picture-in-Picture | `Activity.enterPictureInPictureMode` with the call view (`CallPiP.swift`, `PiPGridPlan.swift`) | none | `MainActivity` is a `FragmentActivity` (for BiometricPrompt); PiP needs `supportsPictureInPicture` in the manifest. The grid plan is the `pip_grid_plan` of section 1. |
| Mini-bar back to the call | The `CallMiniPlayer` idea as a Compose bar | | Pure UI. |

TalkBack from day one (the accessibility rule): the call screen is one stop per control with the iOS words (`CallAccessibility.swift`), a live-region announcement for each phase change (`CallAnnouncements.phase`), 48 dp targets, 200% font.

## 4. What a headless emulator can prove, and what needs two real phones

**On emulators (the CI-style tests we have):**
- All **signalling**: the host partner (a JVM program on LimeCore) can send and receive `call.offer`, `call.answer`, `call.ice`, `call.ringing`, `lime-ctl` and the group ops, so the call machine, the phases, the timeouts, busy and glare, the history, the Calls tab and the notifications are testable with Ada on an emulator and Ben as the partner (as today's staging tests do).
- **A LiveKit room join** from an emulator: LiveKit's Android SDK includes x86 and x86_64 native libraries (README), so a join and a published track should work on an x86_64 emulator with a virtual microphone and camera (the emulator's virtual scene camera and host microphone: **unverified**, never tried here). `livekit-token` and `turn-credentials` work from the staging server for the three test accounts.
- **Media between two apps**: two emulators running lime, one per test account, can call each other end to end (both x86_64, headless, one host). The partner JVM program **cannot** be the media peer: it has no WebRTC (the core is signalling only). So media tests need **a second emulator as the partner** (more host CPU and memory; the night-3 rule "one emulator at a time" would be relaxed for these tests) or the iOS simulator.

**Only on two real phones:** real audio and video quality and echo, Bluetooth headset and car routes, the lock-screen ring and full-screen intent behaviour on a locked real device, PiP gestures, battery and the foreground service surviving a pocketed phone, calls over a bad network and a NAT with the TURN relay (iOS has "Always relay calls", LIME-119), and Play's pre-launch checks.

## 5. What the server and Google learn

**The server:** the same as for iOS and no new metadata, because Android would call the same functions with the same bodies. `turn-credentials {}` (signed-in session, 20 a minute) returns short-lived TURN credentials; the shared secret never leaves the server; media is end to end encrypted between the phones so the relay carries ciphertext. `livekit-token { room, participant }` (20 a minute) returns a token for a **random per-call room id and a random per-call identity** (never the user id), ten minutes to join; the server stores nothing and does not log the room. The LiveKit server sees the participants' IP addresses and that someone connected to a room, as it does for iOS. Signalling ops travel in the normal end-to-end encrypted mailbox (`send_call_signal`). **Google:** nothing about calls today (no FCM for calls until DESIGN-37; then a wake-up token only, per that design). The Telecom and notification APIs are on-device. Play's Data safety form must still list the microphone and camera use (roadmap item a4).

## 6. Proposed split: seven briefs, in this order

| # | Brief | Content | Needs from the user |
|---|---|---|---|
| 1 | **LIME-410 `call_rules.rs`** | The 1:1 and group call machines, history grouping, outcome words and the PiP grid plan into core with Rust tests copied from the Swift cases; Android has no UI yet. | none |
| 2 | **LIME-411 Calls tab and history** | The Calls tab (history grouped, call back or join, missed badge), the call bubble in chats, Settings → call settings; all from the core rules; no media. Tests with the partner sending call ops. | none |
| 3 | **LIME-412 1:1 audio calls** | The chosen WebRTC library, the TURN servers, outgoing and incoming audio, the phases with their announcements, mute, speaker, the foreground service, the notification surface (option B). Partner proves signalling; two emulators prove media. | **WebRTC choice (section 2); approval of a new SDK dependency** |
| 4 | **LIME-413 video and routing** | Camera (CameraX or the WebRTC capturer), video in the call view, camera switch, Bluetooth and earpiece routing. | none after 412 |
| 5 | **LIME-414 the system surface** | Telecom self-managed (if chosen) or the full-screen-intent notification, the lock-screen ring, PiP, the mini-bar. | **Telecom vs notification (section 3)** |
| 6 | **LIME-415 group calls** | LiveKit Android SDK, the sender-key frame encryption, the grid, subject choice, ring or invite from the core machine, join from a chat. | **approval of the LiveKit dependency (Apache-2.0, JitPack repository)**; confirm the key-provider API first (a 30-minute spike inside the brief, with a stop rule) |
| 7 | **LIME-416 two-phone gate and Play declarations** | A script for the two-real-phones test (the list in section 4), the foreground-service and full-screen-intent declarations for Play, the notes. | the user's two phones |

Order logic: 410 and 411 need no new dependency and unblock iOS's adoption; 412 is the first that adds an SDK; 415 is last of the code because its encryption risk should be spiked with the most context. **DESIGN-37 (push) should land before 412 is announced to teachers**, or calls will only ring with the app open.
